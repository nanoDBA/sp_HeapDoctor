# Issue tracker: GitHub

Issues and PRDs for this repo live as GitHub issues at
[`nanoDBA/sp_HeapDoctor`](https://github.com/nanoDBA/sp_HeapDoctor). Use the `gh` CLI for
all operations.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body-file <path>`. Prefer
  `--body-file` over `--body` for anything multi-line: issue bodies here routinely contain
  SQL with single quotes, and `--body` inside a shell heredoc mangles them. (Learned the
  hard way -- a body containing `RAISERROR(N'...')` failed with a bash syntax error.)
- **Read an issue**: `gh issue view <number> --comments`.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments`
  with appropriate `--label` / `--state` filters.
- **Comment**: `gh issue comment <number> --body-file <path>` (or `-F -` with a heredoc).
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: `gh issue comment` **first**, then `gh issue close <number> -r completed`.

Infer the repo from `git remote -v` -- `gh` does this automatically inside a clone.

## Two failure modes worth knowing

**`gh issue close --comment` is a silent no-op on an already-closed issue.** Commit
messages here often auto-close via a keyword, so by the time you go to close an issue it
may already be closed and your comment vanishes with exit code 0. Always
`gh issue comment` as a separate call, then close.

**GitHub's closing-keyword parser is cruder than it looks.**

- `Closes #200, #201, #202` closes **only #200**. The keyword must precede each number.
- The negation in "Filed, **not fixed**: #199" is invisible to it -- it matched `fixed: #199`
  and closed the issue anyway. If a commit must mention an issue it does not resolve,
  phrase it so no keyword immediately precedes the number (e.g. "see #199").

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo starts treating external PRs
as feature requests; `/triage` reads this flag.)_

This is a single-maintainer repo with no external PR flow to date. Leave `no` until one
exists.

When set to `yes`, PRs run through the same labels and states as issues, using the
`gh pr` equivalents (`gh pr view --comments`, `gh pr diff`, `gh pr edit --add-label`).
GitHub shares one number space across issues and PRs, so a bare `#42` may be either --
resolve with `gh pr view 42` and fall back to `gh issue view 42`.

## When a skill says "publish to the issue tracker"

Create a GitHub issue.

## When a skill says "fetch the relevant ticket"

Run `gh issue view <number> --comments`.

## House conventions for this repo

**Every AI-authored issue or comment opens with the triage disclaimer:**

```
> *This was generated by AI during triage.*
```

**Verify before filing.** Claims in this tracker are expected to be checked against the
code first. Three issues (#180, #183, #184) were filed against a line that had been
correct for months and were closed `stale-source`; a fourth (#186) survived scrutiny and
turned out to be real. When filing, quote the file and line, and say what you actually ran.

**State the shortfall when you close.** If an acceptance criterion was not met, or a number
in the issue body turns out to be wrong, say so in the closing comment rather than quietly
ticking the box. #204 was filed claiming "38 exit paths"; the honest figure was 5, and the
close comment corrects it.
